## Brand Strategist

> มุม brand เท่านั้น: positioning, audience, น้ำเสียง/ข้อความ · ไม่พูดเรื่องโค้ด layout หรือ usability
> สถานะ: **Proposed** (ยังไม่ใช่ข้อตัดสินใจ — รอเข้า DECISIONS.md)

### สรุปจุดยืน

จุดขายจริงของสุรเดชไม่ใช่ "เป็นโปรแกรมเมอร์" แต่คือ **คนเดียวที่ดูแลระบบห้องสมุดได้ครบทั้งสาย ตั้งแต่ฐานข้อมูล ตัวแอป ไปจนถึงเซิร์ฟเวอร์** ตอนนี้ PROFILE.md ยังไม่ได้เล่าเรื่องนี้ออกมาชัดพอ ข้อมูลมีครบแล้ว แต่ยังกระจายอยู่ใน Bio ย่อหน้าแรกกับ Brainstorm ("สามบทบาทในคนเดียว") ยังไม่ได้ขึ้นมาเป็นข้อความหลักของแบรนด์

### Positioning: headline กับ tagline

**Headline `Programmer@WALAI AutoLib` — ใช้ได้ แต่ถือภาระ positioning ไว้คนเดียวไม่ไหว**

ข้อดี:
- รูปแบบ `role@place` มีกลิ่นของคนในวงการ dev จำง่าย และดูเป็นลายเซ็นมากกว่าตำแหน่งงานทั่วไป
- ผูกตัวตนเข้ากับผลงานจริง (WALAI AutoLib) ไม่ได้ลอยเป็นคำกว้าง ๆ อย่าง "Full-stack developer"

ปัญหาเชิง brand (ผมยืนยันว่าต้องแก้ด้วย tagline ไม่ใช่ปล่อยไว้):
1. **ขายตัวเองต่ำกว่าความจริง** — คำว่า "Programmer" ตัดบทบาท DBA กับ SysAdmin ทิ้งไป ทั้งที่สองบทบาทนี้คือสิ่งที่ทำให้แตกต่างจากโปรแกรมเมอร์ทั่วไป
2. **คนนอกวงการห้องสมุดไม่รู้จัก "WALAI AutoLib"** — ผู้ว่าจ้างหรือเพื่อน dev ที่ไม่ได้อยู่สายห้องสมุด อ่านแล้วไม่รู้ว่าเป็นระบบอะไร ใหญ่แค่ไหน และทำไมต้องสนใจ
3. **`@` อ่านได้สองแบบ** — คนสาย dev อ่านว่า "ทำงานที่" ส่วนคนทั่วไปอาจอ่านเป็น username หรืออีเมล ใช้เป็น wordmark ได้ แต่ไม่ควรเป็นประโยคเดียวที่อธิบายว่าเขาคือใคร

**ข้อเสนอ:** เก็บ headline ไว้ตามที่เจ้าของเลือก แล้ววาง **tagline หนึ่งบรรทัดไว้ใต้ headline** เพื่อรับหน้าที่อธิบายคุณค่าแทน ตัวเลือกเรียงตามที่ผมชอบ:

- **A (แนะนำ):** "ดูแลระบบห้องสมุดครบทั้งสาย — ฐานข้อมูล · แอปพลิเคชัน · เซิร์ฟเวอร์"
- B: "คนเบื้องหลังระบบห้องสมุด ตั้งแต่ฐานข้อมูลถึงเซิร์ฟเวอร์"
- C: "DBA · Programmer · SysAdmin ในคนเดียว"

ผมเลือก A เพราะบอกทั้ง *ทำอะไร* (ระบบห้องสมุด) และ *ต่างอย่างไร* (ครบทั้งสาย) ส่วน C สั้นและเท่ก็จริง แต่เป็นแค่รายการตำแหน่ง ไม่ได้บอกว่าผู้อ่านได้อะไร

### Audience: ใคร และควรเน้นอะไร

PROFILE ระบุ audience ไว้ 5 กลุ่ม **มากเกินไปสำหรับเว็บส่วนตัวที่มีไม่กี่หน้า** ถ้าพูดกับทุกกลุ่มเท่ากัน ก็จะไม่มีกลุ่มไหนรู้สึกว่าเว็บนี้เขียนมาเพื่อตัวเอง ผมเสนอให้จัดลำดับชัด ๆ แบบนี้:

| ลำดับ | กลุ่ม | เหตุผล | สิ่งที่ควรเห็นก่อน |
|---|---|---|---|
| **หลัก** | คนสาย IT ห้องสมุด + ห้องสมุดอื่นที่สนใจ WALAI AutoLib + ทีมในมหาวิทยาลัย | ที่นี่มีคู่แข่งน้อยมาก และเป็นกลุ่มที่เรื่องของเขาโดดเด่นที่สุด | บทบาทต่อระบบ WALAI AutoLib แบบเล่าจากมุมคนหน้างาน |
| รอง | ผู้ว่าจ้าง / บริษัท | ได้ประโยชน์จากข้อความเดียวกันอยู่แล้ว เพราะ "ดูแลครบทั้งสาย" คือสิ่งที่ผู้ว่าจ้างมองหา | หลักฐานว่าทำได้สามบทบาท + ลิงก์ GitHub |
| เสริม | นักศึกษา / เพื่อนร่วมวงการทั่วไป | ได้แรงบันดาลใจจากเส้นทาง แต่ไม่ใช่เหตุผลหลักที่เว็บนี้มีอยู่ | เรื่อง "จากห้องเรียนสู่ห้องสมุด" ใน About สักหนึ่งย่อหน้าก็พอ |

**จุดยืน:** ความเฉพาะทางด้านห้องสมุดคือ *moat* ของแบรนด์นี้ **อย่าลดทอนให้กลายเป็นพอร์ตโปรแกรมเมอร์ทั่วไป** เพื่อเอาใจผู้ว่าจ้าง ผู้ว่าจ้างที่ใช่จะเห็นคุณค่าของคนที่ดูแลระบบจริงได้ครบวงจรเอง ไม่จำเป็นต้องทำเวอร์ชันแยกเพื่อขายเขา

### 3 ข้อเสนอปรับโทนและข้อความ

**1. Bio ต้องเปิดด้วยคุณค่า ไม่ใช่ลำดับเวลา**

Bio ตอนนี้เรียงเป็น "ตำแหน่ง → เรียนที่ไหน → ตอนนี้ทำอะไร" ย่อหน้าที่ 3 ซ้ำกับ headline และย่อหน้าที่ 2 เป็นไทม์ไลน์ ซึ่งทำให้ประโยคแรกที่คนอ่าน (และประโยคที่มักถูกดึงไปโชว์เป็นสรุป) ยังไม่ขายอะไรเลย ผมเสนอให้เรียงใหม่แบบนี้:
- ประโยคแรก = tagline ในรูปประโยคเต็ม เช่น *"ผมดูแลระบบห้องสมุดอัตโนมัติ WALAI AutoLib ครบทั้งสาย ตั้งแต่ฐานข้อมูล ตัวแอปพลิเคชัน ไปจนถึงเซิร์ฟเวอร์ที่ระบบทำงานอยู่"*
- ประโยคที่สอง = ทำไมเรื่องนี้สำคัญกับผู้อ่าน (เช่น เห็นปัญหาได้ตั้งแต่ต้นจนจบ ไม่ต้องโยนงานข้ามทีม)
- เรื่องการเรียนและการเข้าร่วมงาน ย้ายไปอยู่ส่วน "เส้นทาง" ใน About โดย **ไม่ระบุปีและไม่มีตัวเลขจำนวนปี** ตามที่เจ้าของกำหนด
- เติมข้อความแสดงว่าเป็น **ความเห็นส่วนตัว ไม่ได้พูดแทนมหาวิทยาลัย** ไว้สั้น ๆ (สอดคล้องกับ Avoid และช่วยให้แบรนด์ดูเป็นตัวของตัวเองด้วย)

**2. จาก "รายการเครื่องมือ" เป็น "สามบทบาท"**

Interests ตอนนี้เป็นรายชื่อเทคโนโลยี 6 ตัวเรียงกัน ซึ่งใครก็เขียนแบบนี้ได้ ผมเสนอให้เล่าผ่านกรอบสามบทบาท เพื่อให้เห็นเรื่อง "ครบทั้งสาย" ด้วยตา:
- **ข้อมูล** (DBA) — Oracle
- **สร้าง** (Programmer) — .NET · JavaScript
- **รัน** (SysAdmin) — Linux · Docker · k8s

ส่วน Knowledge ตอนนี้อ่านแล้วเหมือนตำรา (สรุปจากเอกสารทางการ) ซึ่งถูกต้องแต่ **ไม่มีเสียงของเจ้าของเลย** ผมเสนอให้แต่ละเรื่องมีอย่างน้อยหนึ่งประโยคบุรุษที่หนึ่งว่า "ผมใช้สิ่งนี้เพื่ออะไร" แบบกว้าง ๆ โดยไม่เปิดเผยรายละเอียดระบบภายใน เพื่อเปลี่ยนจากหน้าอ้างอิงให้กลายเป็นหน้าที่บอกว่าเขาคิดอย่างไร

**3. นิยามคำว่า "มืออาชีพ" ให้ชัด และคุมโทนสีให้ไปทางเดียวกัน**

"มืออาชีพ" คำเดียวกว้างเกินไป ผมเสนอให้นิยามว่าเป็น **"มืออาชีพแบบคนหน้างาน"**:
- สุภาพ นิ่ง แม่นยำ พูดบุรุษที่หนึ่ง ("ผม") ประโยคสั้น
- ไม่ใช้คำโฆษณาเกินจริง (เช่น "ผู้เชี่ยวชาญระดับสูง", "passionate") ให้ผลงานและบทบาทพูดแทน
- ศัพท์เทคนิคคงเป็นภาษาอังกฤษตามที่คนในวงการใช้ ไม่ฝืนแปล

เรื่องโทนสี (มองจากภาพลักษณ์เท่านั้น): แดง/ชมพู/ขาว สื่อความอบอุ่นและเป็นมิตรได้ดี แต่ **ชมพูมีความเสี่ยงที่จะดูเล่น ๆ ซึ่งขัดกับคำว่ามืออาชีพ** ผมเสนอลำดับแบบนี้: ขาวเป็นพื้นหลัก, แดงเป็นสีเน้นที่ให้ความหนักแน่นและความเชื่อมั่น, ชมพูใช้เป็นสีรองแบบเบา ๆ เท่านั้น ไม่ควรให้ชมพูเป็นสีหลักของหน้า

### สิ่งที่มุม brand จะไม่ยอม (เพื่อเอาไปถกต่อ)

- ตัด WALAI AutoLib ออกจากหน้าแรกเพื่อให้ "ดูกว้างขึ้น" — ผมค้าน เพราะนี่คือจุดที่ทำให้แบรนด์นี้ต่างจากคนอื่น
- ใช้ headline อย่างเดียวโดยไม่มี tagline — ผมค้าน เพราะคนนอกวงการห้องสมุดจะไม่เข้าใจคุณค่า
- เพิ่มตัวเลขประสบการณ์หรือไทม์ไลน์มีปีเพื่อเพิ่มความน่าเชื่อถือ — ผมค้าน เจ้าของไม่ต้องการ และแบรนด์นี้หาความน่าเชื่อถือจาก "ขอบเขตงานที่ดูแล" ได้อยู่แล้ว

### สรุปจุดยืน

**ข้อมูลใน PROFILE.md พร้อมแค่ครึ่งเดียวสำหรับ 4 หน้า** เนื้อหามีพอแล้ว แต่สิ่งที่ผู้เยี่ยมเห็นจริงตอนนี้ต่างจากที่เจ้าของเขียนไว้มาก ตัว parser เก็บแค่ **บรรทัดแรก** ของแต่ละหัวข้อ ผลคือ:

- หน้า **Interests แสดงแค่ "Oracle" ตัวเดียว** ผู้เยี่ยมจะเข้าใจว่าเจ้าของรู้แค่ Oracle ซึ่ง**ทำให้เข้าใจผิด** แย่กว่าไม่แสดงอะไรเลย (`GET /api/interests` ก็คืนค่าแค่ตัวเดียวเหมือนกัน)
- หน้า **About แสดง Bio แค่ย่อหน้าแรก ซึ่งเป็นย่อหน้าเดียวกับที่หน้า Home โชว์ไปแล้ว** คนที่กด About เพื่ออ่านต่อจะได้ข้อความเดิมซ้ำ ไม่ได้อะไรใหม่
- `## Contact` กับ `## Knowledge` **ไม่ถูกอ่านเลย** หน้า Contact กับปุ่ม "ดู GitHub" บนหน้าแรกจึงยังไม่มีแหล่งข้อมูลรองรับ

ปัญหาข้อแรกต้องแก้ก่อนเรื่องอื่นทั้งหมด เพราะเป็นข้อเดียวที่ทำให้ผู้เยี่ยม**ได้ข้อมูลผิด** ไม่ใช่แค่ได้ข้อมูลไม่ครบ

### ความพร้อมของข้อมูลต่อ 4 หน้า

| ข้อมูล | ใช้ที่หน้า | สถานะ | ปัญหาในมุมผู้ใช้ |
|---|---|---|---|
| Name | ทุกหน้า | ✅ พร้อม | — |
| Headline | Home | ✅ พร้อม | คนนอกวงการอ่าน `@` กับ "WALAI AutoLib" ไม่ออก ต้องมีบรรทัดอธิบายต่อท้าย |
| Tagline | Home | ❌ ไม่มีช่องเก็บ | Brand เสนอไว้แต่ PROFILE ยังไม่มีหัวข้อให้ใส่ |
| Bio | About (+ Home) | ⚠️ เนื้อหามี แต่เว็บโชว์แค่ย่อหน้าแรก | About กับ Home ซ้ำกัน |
| Interests | Interests | ⚠️ ชื่อครบ 6 ตัว แต่เว็บโชว์ตัวเดียว | ไม่มีข้อมูลการจัดกลุ่ม · "k8s" เป็นคำย่อที่นักศึกษาและคนสายห้องสมุดอาจไม่รู้จัก |
| Knowledge | Interests (รายละเอียด) | ⚠️ เนื้อหาเยอะ แต่ไม่ถูกอ่าน | ยาวแบบตำรา ไม่มีประโยค "ผมใช้ทำอะไร" · ลิงก์ทั้งหมดไปเอกสารภาษาอังกฤษโดยไม่บอกก่อน |
| Contact | Contact + CTA หน้าแรก | ❌ ไม่ถูกอ่าน | `demo@example.com` เป็น placeholder ถ้าหลุดขึ้นเว็บจะดูเหมือนเว็บยังทำไม่เสร็จ · ไม่ได้บอกว่าช่องทางไหนเป็นช่องทางหลัก |
| Audience | — | ใช้ภายใน | **ไม่ควรโชว์บนเว็บ** แต่ตอนนี้หน้าแรกพิมพ์ "Audience: …" ออกมาตรง ๆ อ่านแล้วเหมือนโน้ตภายในหลุดออกมา |

ข้อสังเกตที่ดี: ชื่อใน `## Interests` ตรงกับหัวข้อ `### ` ใน `## Knowledge` ทุกตัว จึงจับคู่การ์ดกับเนื้อหารายละเอียดได้ทันที **ถ้าจะเปลี่ยนชื่อ (เช่น k8s เป็น Kubernetes) ต้องเปลี่ยนทั้งสองที่พร้อมกัน**

### โครงสร้างข้อมูลที่ควรตกลงก่อน Lab 04

- **Interests:** รายการใน `## Interests` ต้องเป็น**ชื่อล้วน**ต่อไป (เป็น contract ของเว็บและ API) ห้ามเติมคำอธิบายหรือบทบาทต่อท้ายชื่อในบรรทัดเดียวกัน เพราะชื่อจะไม่ตรงกับหัวข้อ Knowledge อีก ถ้าจะจัดกลุ่มตามบทบาท ให้ตกลงใน DECISIONS ว่าข้อมูลการจัดกลุ่มเก็บไว้ที่ไหน (เช่น เพิ่มหัวข้อแยก) แทนการยัดรวมไว้ในรายการ
- **Knowledge ต่อหัวข้อ:** ควรมีสามชั้นให้ผู้อ่านเลือกลึกได้เอง: (1) ประโยคเดียว "ผมใช้ X เพื่อ…" (2) สรุปที่มีอยู่แล้ว (3) ลิงก์อ่านต่อ ชั้นแรกยังไม่มีเลย
- **Contact:** ตัดสินให้ชัดว่า **ฟอร์มคือช่องทางหลัก และ GitHub คือช่องทางรอง ไม่แสดงอีเมลบนเว็บ** (สอดคล้องกับ Avoid) แล้วเอา `demo@example.com` ออกจากสิ่งที่เว็บจะแสดง
- **Tagline:** ถ้าเห็นด้วยกับ Brand ต้องมีหัวข้อเก็บใน PROFILE (ต้องตกลงชื่อหัวข้อก่อน เพราะหัวข้อใน PROFILE คือ contract)

### จุดที่ผู้เยี่ยมจะสับสน

1. **Interests โชว์ตัวเดียว** (ดูสรุปจุดยืนด้านบน) ร้ายแรงที่สุด

6. **ภาษาปนกัน** เมนู ป้ายฟอร์ม ปุ่ม และข้อความสถานะเป็นอังกฤษ ("Send", "Sent. Thank you!") แต่เนื้อหาเป็นไทย และหน้าเว็บประกาศตัวเองเป็นภาษาไทย
7. **สรรพนามไม่ตรงกัน** Bio ใช้ "ผม" แต่การ์ดหน้าแรกเขียนว่า "ส่งข้อความถึง**ฉัน**" เสียงของเจ้าของเว็บต้องเป็นคนเดียวกันทั้งเว็บ
8. **ฟอร์มขออีเมลแต่ไม่บอกว่าเอาไปทำอะไร** ผู้เยี่ยมที่ระวังเรื่องข้อมูลส่วนตัว (โดยเฉพาะคนในมหาวิทยาลัย) จะลังเล
9. **ข้อความ error หลุดถึงผู้ใช้** ตอนนี้ฟอร์มแสดง `Error: <ข้อความจาก server>` ตรง ๆ ผู้เยี่ยมจะเห็นอะไรอย่าง `NOT_IMPLEMENTED: …` ซึ่งไม่มีความหมายสำหรับเขา
10. **ลิงก์ออกนอกเว็บไม่บอกก่อน** ลิงก์ Knowledge ทุกตัวไปเอกสารทางการภาษาอังกฤษ ผู้อ่านไทยควรรู้ก่อนกด
11. **หน้าแรกมีป้าย "Personal branding site"** เป็นคำของคอร์ส ไม่ใช่คำที่ผู้เยี่ยมต้องรู้

### จุดที่ไม่เห็นด้วยกับ Brand Strategist

1. **Bio ประโยคแรก = tagline ในรูปประโยคเต็ม — ไม่เห็นด้วยถ้าใช้บนหน้าแรก** ถ้าหน้าแรกมี Headline + tagline + Bio ที่เปิดด้วยข้อความเดียวกันอีก ผู้เยี่ยมจะอ่านข้อความ "ครบทั้งสาย" **สามรอบในหน้าจอเดียว** ผมเห็นด้วยกับการเรียง Bio ใหม่ แต่ Bio ต้องอยู่ที่ About เท่านั้น หน้าแรกจบที่ tagline แล้วตามด้วยปุ่ม
2. **ชื่อกลุ่ม "ข้อมูล / สร้าง / รัน" — ไม่เห็นด้วย** คำกริยาคำเดียวแบบนี้ผู้อ่านต้องเดาเอง โดยเฉพาะ "รัน" ที่คนนอกวงการไม่รู้ว่าหมายถึงดูแลเซิร์ฟเวอร์ ผมเสนอให้ใช้คำชุดเดียวกับ tagline A เพื่อให้ผู้อ่านจับคู่ได้เอง: **ฐานข้อมูล (DBA) · แอปพลิเคชัน (Programmer) · เซิร์ฟเวอร์ (SysAdmin)** คำที่ผู้อ่านเห็นบนหน้าแรกกับบนหน้าเทคโนโลยีต้องเป็นคำเดียวกัน
3. **กลุ่มเป้าหมายหลักกำหนดโครงสร้างเว็บ — เห็นต่างบางส่วน** ผมยอมรับว่า Brand เลือกกลุ่มหลักจากจุดที่ทำให้แตกต่าง (คนสายห้องสมุด) และข้อความแบรนด์ควรพูดกับกลุ่มนั้น แต่ **IA และคำอธิบายต้องออกแบบเพื่อคนที่มีโอกาสหลงมากที่สุด** คือคนนอกวงการ (ผู้ว่าจ้าง นักศึกษา ที่มักเข้ามาจากลิงก์ GitHub) คนสายห้องสมุดรู้จัก WALAI AutoLib อยู่แล้ว บรรทัดอธิบายไม่ทำให้เขาเสียอะไร แต่ถ้าไม่มี คนนอกวงการจะเลิกอ่านทันที
4. **เก็บชื่อ "Interests" ไว้แล้วเติมกรอบสามบทบาทเข้าไป — ไม่เห็นด้วย** ถ้าเนื้อหาเปลี่ยนเป็นแผนที่ความสามารถ ชื่อเมนูก็ต้องเปลี่ยนตาม ไม่อย่างนั้นป้ายจะบอกอย่างหนึ่งแต่เนื้อหาเป็นอีกอย่าง
5. **จุดที่เห็นด้วยและขอเสริม:** เรื่องไม่มีปีและไม่มีตัวเลขจำนวนปี, การใส่คำชี้แจงว่าเป็นความเห็นส่วนตัว (ผมเสนอให้วางไว้ท้ายเว็บทุกหน้า ไม่ใช่แค่ใน Bio) และการเติมประโยคบุรุษที่หนึ่งใน Knowledge ส่วนเรื่องสีชมพู มุม UX ขอเพิ่มเงื่อนไขเดียว: **ห้ามใช้ชมพูเป็นสีตัวอักษรหรือสีปุ่มบนพื้นขาว** เพราะ contrast มักไม่ผ่าน a11y ให้ใช้เป็นพื้นหลังหรือเส้นตกแต่งเท่านั้น

- ขึ้นเว็บทั้งที่หน้า Interests ยังโชว์ไม่ครบ 6 รายการ — ผมค้าน เพราะผู้ใช้ได้ข้อมูลผิด ไม่ใช่แค่ได้ไม่ครบ

### สรุปจุดยืน

ทั้ง Brand และ UX คุยกันว่า **"เล่าอะไรให้ดีขึ้น"** แต่ยังไม่มีใครถามว่า **"เล่าไปแล้วใครเอาไปใช้ทำอะไรได้บ้าง"** เว็บนี้บอกโลกว่าเจ้าของคือ **ผู้ถือสิทธิ์สูงสุดของระบบจริงในองค์กรที่ระบุชื่อได้** (DBA + SysAdmin) ติดชื่อจริง ชื่อที่ทำงาน ชื่อที่เรียน และลิงก์ GitHub ในหน้าเดียว และยังจะเปิดช่องให้คนแปลกหน้าเขียนข้อความขึ้นหน้าเว็บ (Guestbook) ด้วยโค้ดที่ตอนนี้ **มีช่องโหว่ XSS อยู่แล้ว** ผมเห็นว่ารอบนี้ควร ship ให้ **เล็กกว่าที่ Brainstorm/Brand/UX เสนอ** แล้วค่อยเพิ่มทีละชิ้นเมื่อตอบคำถามด้านล่างได้

### ความเสี่ยง (เรียงจากร้ายแรงสุด)

**R1 · Stored XSS + spam ใน Guestbook — ร้ายแรงที่สุด และมีอยู่ในโค้ดตอนนี้แล้ว**
- `src/pages/guestbook.astro` เอา `e.name` / `e.message` ไปต่อ string แล้วยัดเข้า `innerHTML` ตรง ๆ ไม่มี escape ใด ๆ เมื่อ Lab 05 ทำให้ API บันทึกได้จริง ใครก็โพสต์ `<img onerror=…>` แล้วสคริปต์นั้นจะรันในเบราว์เซอร์ของ **ทุกคนที่เปิดหน้า Guestbook** ภายใต้โดเมนที่มีชื่อเจ้าของเว็บ
- `maxlength` อยู่ฝั่ง HTML เท่านั้น ยิง `POST /api/guestbook` ตรงก็ข้ามได้ ไม่มี rate limit ไม่มี honeypot/captcha ไม่มีการกลั่นกรองก่อนแสดง
- **ไม่มีทางลบ** — Avoid ตัดระบบ login/admin ออกไปแล้ว ถ้ามีคนโพสต์คำหยาบ ลิงก์พนัน หรือข้อความหมิ่นประมาทใต้ชื่อพนักงานมหาวิทยาลัย ทางเดียวคือเข้าไปแก้ SQLite ใน volume ของ Coolify ด้วยมือ
- งานนี้คร่อมสองฝั่ง: escape ตอน render เป็นของ UI (Claude) · validate/จำกัดความยาว/rate limit เป็นของ API (OpenCode) — ถ้าต่างฝั่งต่างคิดว่าอีกฝั่งทำ ช่องโหว่จะรอดไปถึง production

**R2 · ระบุตัวตนซ้ำและคำนวณอายุได้ แม้ไม่ใส่ปีหรือนามสกุล**
- เจ้าของสั่งชัดว่าไม่เอานามสกุลและปีที่เริ่มเรียน/ทำงาน แต่ Bio ย่อหน้าที่ 2 บอก **ชื่อสถาบันที่เรียน + "เข้าร่วมงานหลังสำเร็จการศึกษา"** เมื่อรวมกับชื่อจริง ชื่อที่ทำงาน และตำแหน่ง คนที่ตั้งใจจะหาข้อมูลสามารถไปหาต่อจากทำเนียบบุคลากร ประกาศรับสมัคร หรือรายชื่อบัณฑิต แล้ว **ย้อนหาทั้งนามสกุลและช่วงอายุได้** — ข้อห้ามเรื่องปีจึงถูกเลี่ยงได้ด้วยข้อมูลที่เราใส่เอง
- ปุ่ม "ดู GitHub" พาไปที่ตัวตนที่ **ใหญ่กว่าเว็บ**: ชื่อ/รูปโปรไฟล์ repo อื่น ๆ วันที่สร้างบัญชี และ **อีเมลผู้เขียนใน git commit** ของทุก repo สาธารณะ — ยังไม่มีใครตรวจว่าตรงนั้นขัดกับ Avoid หรือไม่
- repo ของเว็บนี้เองก็เป็นช่องทาง: ถ้า repo เป็นสาธารณะ ทุกอย่างใน `docs/` (รวม PROFILE ส่วนที่เว็บไม่แสดง, DEBATE นี้, ประวัติ commit ในอนาคต) **อ่านได้หมด** การ "ไม่แสดงบนเว็บ" ไม่ได้แปลว่า "ไม่เปิดเผย" (ตรวจแล้ว: ประวัติ PROFILE ในตอนนี้ยังไม่มีตัวเลขปี — ต้องรักษาไว้แบบนี้ และห้ามเผลอเขียนลงไปใน commit message หรือ handoff)
- มุม "จากห้องเรียนสู่ห้องสมุด" ของ Brainstorm และ "เส้นทาง: เรียน → เข้าร่วมงาน" ของ UX คือการ **ขยายข้อมูลที่ใช้ระบุตัวตน ให้เด่นขึ้น** ทั้งที่เป็นส่วนที่เสี่ยงที่สุด

**R3 · Overclaim — "ครบทั้งสาย" อาจกลายเป็นคำอ้างที่ถูกจับผิดได้**
- Brand เขียนว่าจุดขายคือ **"คนเดียวที่ดูแลระบบห้องสมุดได้ครบทั้งสาย"** และ tagline A "ดูแลระบบห้องสมุดครบทั้งสาย" อ่านได้ว่า **เขาเป็นคนเดียวที่ดูแล WALAI AutoLib ทั้งระบบ** ถ้าในความจริงมีทีม มีหัวหน้า มีผู้พัฒนาคนอื่น คนในวงการห้องสมุด (ซึ่ง Brand เลือกเป็นกลุ่มหลัก) คือกลุ่มที่ **รู้ดีที่สุดว่าจริงหรือไม่** — ทำให้กลุ่มหลักเป็นกลุ่มแรกที่จะหมดความเชื่อถือ และอาจกระทบความสัมพันธ์กับเพื่อนร่วมงาน
- Headline `Programmer@WALAI AutoLib` บวกชื่อผลิตภัณฑ์บนหน้าแรก อาจถูกอ่านว่าเป็น **ช่องทางทางการของผลิตภัณฑ์** ห้องสมุดอื่นที่ "สนใจระบบ" อาจติดต่อมาเรื่องซื้อ/ซัพพอร์ต — เท่ากับพูดแทนมหาวิทยาลัยโดยไม่ตั้งใจ คำชี้แจงท้ายเว็บช่วยได้บางส่วนแต่ไม่หมด
- Interests มี **k8s** — ถ้าไม่ได้ใช้ใน production จริง แต่ Brand จัดเข้ากลุ่ม "SysAdmin" และ UX เปลี่ยนชื่อหน้าเป็น "เทคโนโลยีที่ใช้" ความหมายจะเปลี่ยนจาก "สนใจ" เป็น **"ทำเป็น"** ทันที ผู้ว่าจ้างจะถามลึกในสัมภาษณ์
- Knowledge ตอนนี้เป็นสรุปเอกสารทางการ 6 เรื่อง รูปประโยคแบบตำรา — คนในวงการอ่านแล้วอาจสรุปว่า **"ก๊อปมา/ให้ AI เขียน"** ซึ่งทำร้ายความน่าเชื่อถือมากกว่าไม่มีหน้านี้เลย

**R4 · เปิดเผยโครงสร้างระบบภายในและทำตัวเองเป็นเป้า phishing**
- Avoid ห้าม hostname/IP/schema/เวอร์ชัน แต่ทั้ง Brand และ UX เสนอให้เติมประโยค **"ผมใช้ X เพื่อ…"** ในทุกเทคโนโลยี และ Brainstorm มีหน้า "WALAI AutoLib ในมุมผม" — รวมกันแล้วกลายเป็น **แผนที่ stack ของระบบห้องสมุดในมหาวิทยาลัยที่ระบุชื่อได้** (Oracle + Linux + Docker + k8s) ทีละประโยคอาจดูไม่อันตราย แต่รวมกันคือ reconnaissance ที่คนโจมตีไม่ต้องหาเอง
- ข้อความ "ดูแลตั้งแต่ฐานข้อมูลถึงเซิร์ฟเวอร์" = ประกาศว่า **บัญชีของคนนี้มีสิทธิ์สูงสุด** เว็บ + ฟอร์มติดต่อ + GitHub คือช่องทางที่คนแปลกหน้าจะใช้ส่ง spear-phishing ("ห้องสมุด X สนใจระบบ ขอให้ดูไฟล์แนบ")
- `src/lib/db.ts` กับ API route คืน `err.message` ดิบกลับไปใน JSON และ `contact.astro` แสดง `Error: …` ตรง ๆ — เมื่อ Lab 05 ใช้งานจริง error อย่าง constraint failed ของ SQLite จะพ่น **ชื่อตารางและคอลัมน์** ให้ผู้ใช้เห็น ซึ่งขัดกับ Avoid ข้อ "schema" และ `public-site-safe` โดยตรง (JSON ที่ส่งมาผิดรูปก็จะคืนข้อความ parser ออกไปเช่นกัน)

**R5 · ฟอร์มติดต่อ = เก็บข้อมูลส่วนบุคคลของคนอื่น แต่ไม่มีใครอ่าน**
- ฟอร์มเก็บ ชื่อ + อีเมล + ข้อความ ลง SQLite ใน volume แต่ **ไม่มีการแจ้งเตือนเจ้าของ** เมื่อมีข้อความเข้า จะรู้ได้ก็ต่อเมื่อเข้าไปเปิดไฟล์ DB เอง — UX เสนอให้ฟอร์มเป็น **"ช่องทางหลัก"** แต่ในทางปฏิบัติมันคือกล่องที่ไม่มีใครเปิด ผู้ว่าจ้างส่งมาแล้วไม่ได้คำตอบ = เสียโอกาสและเสียภาพลักษณ์
- เก็บข้อมูลส่วนบุคคลของผู้อื่น → มีภาระตาม PDPA: แจ้งวัตถุประสงค์ ระยะเวลาเก็บ การลบเมื่อขอ ใครเข้าถึง volume ได้บ้าง ข้อความของ UX "ใช้สำหรับตอบกลับเท่านั้น ไม่แสดงบนเว็บ" คือ **คำสัญญา** — ถ้าไม่มี retention/ลบจริง คำสัญญานั้นเป็นเท็จ
- ไม่มี rate limit เหมือน Guestbook → spam bot เติม DB จน volume เต็มได้ และถ้าเจ้าของ export ข้อความมาอ่านในเครื่องมืออื่น ข้อความพวกนี้ก็เป็น input ที่ไม่น่าไว้ใจเช่นกัน

**R6 · พูดแทน/ผูกแบรนด์ตัวเองกับองค์กร**
- ใช้ชื่อมหาวิทยาลัยและชื่อผลิตภัณฑ์เป็นแกนของแบรนด์ส่วนตัว โดยยังไม่มีใครถามว่า **นโยบายของต้นสังกัดอนุญาตให้บุคลากรเล่าเรื่องระบบภายในบนเว็บส่วนตัวหรือไม่** คำชี้แจงท้ายเว็บไม่ได้ทดแทนการขออนุญาต
- Brand เรียกความเป็นห้องสมุดว่า *moat* — แต่ moat นั้น **เป็นของนายจ้าง ไม่ใช่ของเจ้าของเว็บ** วันที่ย้ายงานหรือระบบเปลี่ยนชื่อ แบรนด์ทั้งก้อนต้องเขียนใหม่

**R7 · Scope creep ซ่อนอยู่ใน "Must" และในข้อเสนอของทั้งสองฝั่ง**
- Must ข้อ About "ครบ 3 ย่อหน้า (ต้องแก้ parser ก่อน)" และข้อ Interests "ลิงก์ไปเนื้อหา Knowledge" คือการ **ขยาย contract ของ `profile.ts`** (อ่าน `###` ย่อยใน Knowledge, อ่านหลายย่อหน้า) ซึ่ง ownership ของ `src/lib/profile.ts` ยังไม่ได้ระบุในตารางว่าเป็นฝั่งไหน — เสี่ยงสองฝั่งแก้ชนกัน และทุกการแก้ parser เสี่ยงให้หน้าเว็บตกไปเป็น stub **แบบเงียบ** (ไม่มี error)
- Brand เพิ่ม: tagline (หัวข้อใหม่ใน contract), เขียน Bio ใหม่, ประโยคบุรุษที่หนึ่ง 6 เรื่อง · UX เพิ่ม: หัวข้อจัดกลุ่มสามบทบาท, การ์ดขยายได้, footer disclaimer ทุกหน้า, logic ซ่อนฟอร์มเมื่อ API ไม่พร้อม, เปลี่ยนชื่อเมนู, microcopy ทั้งชุด — **รวมกันใหญ่กว่า Must เดิมหลายเท่า** และทั้งหมดยังไม่มี done criteria

### คำถามที่ต้องตอบก่อน ship

1. ใครเป็นเจ้าของการ escape ข้อความ Guestbook ตอน render และใครทำ rate limit — เขียนชื่อฝั่งไว้ใน DECISIONS แล้วหรือยัง? ถ้ายังตอบไม่ได้ Guestbook ขึ้นไม่ได้
2. ถ้ามีคนโพสต์ข้อความที่ไม่เหมาะสมตอนตีสอง เจ้าของ **ลบได้ภายในกี่นาที และด้วยวิธีไหน** (ไม่มี admin)?
3. เมื่อมีข้อความเข้าฟอร์มติดต่อ เจ้าของ **รู้ได้อย่างไร** และตั้งใจตอบภายในกี่วัน? ถ้าไม่มีคำตอบ ฟอร์มจะเป็น "ช่องทางหลัก" ได้อย่างไร
4. เก็บข้อความติดต่อไว้นานเท่าไร ลบอย่างไร และใครเข้าถึง volume บน Coolify ได้บ้าง?
5. ประโยค "ดูแลครบทั้งสาย" — ถ้าหัวหน้าหรือเพื่อนร่วมทีมอ่าน จะเห็นด้วยทุกคำไหม? มีคนอื่นดูแลส่วนใดของ WALAI AutoLib อยู่หรือเปล่า?
6. ทุกเทคโนโลยีใน Interests — เจ้าของใช้จริงในงาน หรือแค่สนใจ/เคยลอง? (โดยเฉพาะ k8s) ถ้าหน้าจะชื่อ "เทคโนโลยีที่ใช้" ต้องตอบข้อนี้ให้ได้ทุกตัว
7. ต้นสังกัดมีนโยบายเรื่องบุคลากรเผยแพร่ข้อมูลเกี่ยวกับระบบภายในหรือใช้ชื่อองค์กร/ผลิตภัณฑ์บนเว็บส่วนตัวไหม? ถามแล้วหรือยัง?
8. ตรวจบัญชี GitHub ที่จะลิงก์แล้วหรือยัง — ชื่อที่แสดง รูป repo อื่น และ **อีเมลใน commit** ขัดกับ Avoid ไหม?
9. repo ของเว็บนี้จะเป็น public หรือ private? ถ้า public ยอมรับได้ไหมว่า `docs/` ทั้งโฟลเดอร์ (รวมไฟล์นี้) อ่านได้ทุกคน?
10. จำเป็นต้องระบุชื่อสถาบันที่เรียนหรือไม่ — มันช่วยกลุ่มเป้าหมายหลัก (คนสายห้องสมุด) ตรงไหน เทียบกับความเสี่ยงที่ทำให้ย้อนหาอายุได้?
11. error ทุกแบบที่ API คืนให้ผู้ใช้ ผ่านการเปลี่ยนเป็นข้อความสั้นที่ไม่มีชื่อตาราง/คอลัมน์/stack แล้วหรือยัง (ทดสอบด้วย JSON ผิดรูปและช่องว่างเปล่า)?
12. done criteria ของรอบนี้คืออะไร — ข้อเสนอของ Brand/UX ข้อไหน **ไม่** ทำรอบนี้?

### จุดที่ไม่เห็นด้วยกับ Brand Strategist

1. **"คนเดียวที่ดูแลได้ครบทั้งสาย" / tagline A = overclaim เสี่ยงสูง** — ขอให้เปลี่ยนเป็นขอบเขตที่พิสูจน์ได้และไม่อ้างความเป็นผู้เดียว เช่น "ทำงานกับระบบห้องสมุด ตั้งแต่ฐานข้อมูลถึงเซิร์ฟเวอร์" และห้ามใช้คำว่า "คนเดียว" ในทุกข้อความ (R3)
2. **ประโยค "ผมใช้ X เพื่อ…" ทุกเทคโนโลยี** — ไม่เห็นด้วยในรูปที่เสนอ ถ้าจะมี ต้องพูดในระดับทักษะทั่วไป ("ผมสนใจเรื่อง transaction และ concurrency") ไม่ใช่ระดับระบบ ("ระบบห้องสมุดของเรารันบน…") (R4)
3. **ความเป็นห้องสมุดคือ moat และห้ามเอา WALAI AutoLib ออกจากหน้าแรก** — ผมไม่ได้บอกให้เอาออก แต่ค้านการยึดแบรนด์ส่วนตัวไว้กับผลิตภัณฑ์ขององค์กรก่อนได้คำตอบเรื่องนโยบายต้นสังกัด (R6)
4. **จัด Interests เป็นสามบทบาท** — ทำให้ "ความสนใจ" กลายเป็น "ความสามารถที่อ้าง" ต้องผ่านคำถามข้อ 6 ก่อน

### จุดที่ไม่เห็นด้วยกับ UX Critic

1. **ฟอร์มคือช่องทางหลัก** — ไม่เห็นด้วยจนกว่าจะมีวิธีแจ้งเตือนเจ้าของและนโยบายเก็บ/ลบข้อมูล ระหว่างนี้ GitHub (หรือช่องทางอื่นที่เจ้าของเลือก) ควรเป็นช่องทางหลัก (R5)
2. **เปลี่ยนชื่อหน้าเป็น "เทคโนโลยีที่ใช้"** — แก้ความกำกวมของป้าย แต่เพิ่ม overclaim ถ้ายังไม่ยืนยันข้อ 6 (R3)
3. **"เส้นทาง: เรียน → เข้าร่วมงาน → บทบาทปัจจุบัน" ใน About** — แม้ไม่มีปี แต่ทำให้ข้อมูลที่ใช้ย้อนหาอายุเด่นขึ้น (R2)
4. **IA ที่เสนอเพิ่มงานจำนวนมาก** (หัวข้อจัดกลุ่ม การ์ดขยายได้ logic ซ่อนฟอร์ม footer ทุกหน้า) — เห็นด้วยกับทิศทาง แต่ต้องแบ่งเป็น "รอบนี้" กับ "รอบหน้า" พร้อม done criteria (R7)
5. **"ซ่อนฟอร์ม/Guestbook เมื่อ API ไม่พร้อม"** — ไม่พอ ปัญหาหลักไม่ใช่ตอน API **ไม่พร้อม** แต่คือตอน API **พร้อมแล้ว** และหน้า Guestbook render HTML ของคนแปลกหน้าโดยไม่ escape (R1)

### จุดที่เห็นด้วยกับทั้งสองฝั่ง

- ไม่มีปีและไม่มีตัวเลขจำนวนปี · มีคำชี้แจงว่าเป็นความเห็นส่วนตัว · ห้ามโชว์ Audience/placeholder อีเมล · ห้ามแสดง error ดิบจาก server · แก้หน้า Interests ให้แสดงครบก่อน ship

### สิ่งที่มุม Devil's Advocate จะไม่ยอม (เพื่อเอาไปถกต่อ)

- Deploy Guestbook ขณะที่ยัง render ด้วย `innerHTML` โดยไม่ escape หรือยังไม่มีวิธีลบข้อความ — ผมค้าน
- ข้อความใดบนเว็บที่อ้างว่าเจ้าของดูแลระบบ "คนเดียว" หรือ "ทั้งหมด" โดยไม่ได้ยืนยันกับความเป็นจริงในทีม — ผมค้าน
- เผยแพร่ชื่อสถาบันที่เรียนคู่กับลำดับเหตุการณ์ "จบแล้วเข้าทำงาน" — ผมค้าน จนกว่าเจ้าของจะยืนยันว่ายอมรับความเสี่ยงเรื่องการย้อนหาอายุ
- เปิดฟอร์มเก็บอีเมลของผู้อื่นโดยไม่มีประกาศการใช้ข้อมูลและไม่มีคนอ่าน — ผมค้าน
